# TravelPilot conceptual notes and interview preparation

This file captures questions and answers that arise while building TravelPilot. It is intentionally written in an interview style. Add new questions as each learning milestone is completed.

## LangChain4j and AI Services

### What is LangChain4j?

LangChain4j is a Java library that provides abstractions for chat models, AI Services, tools, structured output, RAG, memory, vector stores, and agentic applications. It hides provider-specific details behind Java-friendly APIs.

### What is an AI Service?

An AI Service is a Java interface whose implementation is generated by LangChain4j. The interface describes the application-level operation, while LangChain4j handles prompt construction, model invocation, tool execution, and output parsing.

In TravelPilot, `TravelPlannerAgent` is an AI Service interface.

### Is `TravelPlannerAgent` a normal Java implementation?

No. It is a runtime-generated proxy. The interface has no method implementation; the proxy intercepts `chat(...)`, constructs a LangChain4j request, calls the configured `ChatModel`, and converts the result into `TravelPlan`.

### What is the difference between `@AiService` and `AiServices.builder(...)`?

`@AiService` allows the Spring Boot starter to discover the interface and create the proxy automatically.

`AiServices.builder(...)` creates the same kind of proxy explicitly. Explicit construction is useful when the application needs direct control over the model, tools, listeners, memory, or tool-call limits.

TravelPilot uses explicit construction in `TravelPilotAiConfiguration` so the important AI wiring is visible in one place.

### What happens when `agent.chat(message)` is called?

1. The proxy reads the system prompt and user message.
2. LangChain4j discovers the configured tools.
3. It creates a model request containing messages, tools, and response-format information.
4. The configured `ChatModel` sends the request to Ollama.
5. Ollama either returns a final response or requests one or more tools.
6. LangChain4j executes requested tools and sends their results back to the model.
7. The model produces the final structured response.
8. LangChain4j deserializes the response into `TravelPlan`.

### What is the role of `@SystemMessage`?

`@SystemMessage` defines stable behavior and constraints for the AI Service. In TravelPilot it tells the assistant to ask for missing travel information, use tools for availability, avoid invented prices, and never claim that a booking was completed.

System prompts are instructions, not security boundaries. The application must still validate tool arguments and enforce authorization outside the model.

## Tools and function calling

### What is a LangChain4j tool?

A tool is a Java method exposed to the language model. The model does not execute Java directly. It produces a structured tool-call request, and LangChain4j invokes the corresponding Java method.

TravelPilot exposes `searchFlights(...)` and `searchHotels(...)` through `TravelSearchTools`.

### Why should a tool have a clear description?

The model uses the tool name, description, parameter names, parameter types, and parameter descriptions to decide when and how to call it. A vague tool description increases incorrect or unnecessary calls.

### What should a production tool do before calling an external service?

A tool should validate arguments, apply authorization, enforce timeouts, limit result sizes, handle provider errors, avoid leaking secrets, and return a stable domain-level result. Side-effecting tools should also be idempotent and require an approval boundary where appropriate.

### Why does TravelPilot use ports and mock providers?

`FlightSearchPort` and `HotelSearchPort` isolate the application from provider implementations. The mock providers make the AI workflow deterministic and testable before connecting real airline or hotel APIs.

### What is the difference between a tool call and a normal service call?

A normal service call is selected deterministically by application code. A tool call is selected by the model based on the tool schema and the user request. The tool implementation itself should remain deterministic and should not trust the model blindly.

## Structured output

### Why does `TravelPlannerAgent` return `TravelPlan` instead of `String`?

A typed return value gives the API and UI a stable contract. The frontend can render status, flights, hotels, assumptions, and warnings without parsing natural-language text.

### Does structured output make the model data trustworthy?

No. Structured output validates the shape of the response, not the truth of its contents. Prices, availability, IDs, and provider facts must come from tools or trusted application data.

### What are the important `TravelPlan` statuses?

- `NEEDS_CLARIFICATION`: required information is missing.
- `READY`: suitable options are available.
- `NO_RESULTS`: the tools completed but found no matching options.

## Ollama and HTTP endpoints

### Does the browser call Ollama directly?

No. The browser calls Spring Boot at:

```text
POST /api/v1/chat
```

Spring Boot calls LangChain4j, and LangChain4j calls Ollama at:

```text
POST http://localhost:11434/v1/chat/completions
```

The second endpoint is provided by Ollama's OpenAI-compatible API. It is not a controller in TravelPilot.

### Why is an OpenAI client used for Ollama?

Ollama exposes an OpenAI-compatible HTTP API. LangChain4j's OpenAI integration can therefore send requests to Ollama by changing the base URL and model configuration, while the application keeps a provider-independent LangChain4j API.

### What happens if Ollama is slow?

The HTTP client can time out, and LangChain4j may retry the request. Retries increase the total number of model calls and latency. Timeout, retry count, model size, thinking mode, prompt size, and tool/structured-output complexity all affect response time.

## Tool-call loops and observability

### What does `maxToolCallingRoundTrips(2)` control?

It limits the number of model responses that contain tool calls during one AI Service invocation. It limits tool-calling rounds, not the total number of individual tools and not HTTP retries.

For example:

```text
Initial model request
Tool-call response and tool execution: round 1
Final model response
```

This normally produces two successful model requests.

### How can the application count model requests?

A `ChatModelListener` can log `onRequest`, `onResponse`, and `onError`. The listener observes the LangChain4j request and response, including messages and available tools.

### Does the listener run once for every retry?

Not necessarily. LangChain4j's listener lifecycle is associated with the model interaction, while the HTTP client may perform internal retries. Retry logging and model-invocation logging should therefore be interpreted separately.

### How can the proxy be debugged?

The interface itself has no method body. Debugging should happen at these boundaries:

- Before and after the `agent.chat(...)` call.
- Inside `ChatModelListener`.
- Inside `TravelSearchTools`.
- Inside provider ports and mock providers.
- Inside LangChain4j source code when investigating proxy behavior.

For complete control, replace automatic AI Service registration with an explicit `AiServices.builder(...)` bean or use the lower-level `ChatModel` API.

## State, memory, and architecture

### Is `conversationId` currently memory?

No. TravelPilot currently passes `conversationId` through the HTTP response, but it does not pass it as a LangChain4j memory ID or persist conversation messages. The current flow is stateless.

### What is the difference between chat history and memory?

Chat history is the conversation that the user sees. Memory is the context supplied to the model to preserve useful information across calls. Memory may summarize, evict, transform, or enrich history.

### What should be added during the memory milestone?

Add per-conversation chat memory, persistent storage, user preferences, task state, eviction/summarization, and tests that verify two requests in the same conversation share the intended context.

## RAG and vector search

### What is RAG?

Retrieval-Augmented Generation retrieves relevant application-owned content and supplies it to the model before generation. It allows the model to answer using current or private knowledge without retraining the model.

### What will TravelPilot use RAG for?

TravelPilot can use RAG for baggage rules, cancellation policies, hotel policies, visa guidance, and destination information. Availability and prices should remain tool/provider data, not RAG data.

### What should a good RAG response include?

It should include an answer grounded in retrieved documents, source citations, an explicit no-answer behavior, and protection against instructions embedded inside retrieved documents.

## Future agentic topics

### What is MCP?

MCP is a protocol for exposing tools and resources through a standardized client/server interface. TravelPilot can later expose travel tools through an MCP server and consume them from the orchestrator.

### What is LangGraph4j useful for?

LangGraph4j is useful when the application needs explicit state, branching, retries, checkpoints, bounded loops, and human approval steps. It makes workflow control visible instead of leaving all orchestration to an unconstrained model.

### When should multiple agents be introduced?

Only after the single-agent workflow is understood and tested. TravelPilot can later separate search, policy, itinerary, and critique responsibilities, but multi-agent design adds coordination, cost, latency, and failure modes.

### Where does gRPC fit?

gRPC is appropriate for typed internal service-to-service communication, such as a mock availability service. It is different from MCP: gRPC is primarily an application service protocol, while MCP is an AI-tool interoperability protocol.

### What should AI testing measure?

Tests should cover tool correctness, structured-output validity, retrieval quality, groundedness, task success, prompt-injection resistance, latency, token usage, cost, and graceful failure behavior.

### What are important agent security risks?

Prompt injection, indirect instruction injection from documents or tools, excessive agency, unbounded loops, data leakage, insecure tool permissions, memory poisoning, and uncontrolled side effects.
